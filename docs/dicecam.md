# Physical dice and the dicecam

The table can play with real dice (PROMPTS.md, prompts 18 and 19). "Physical dice" is switched on from the options screen and recorded as a `dice/physical` event. From then on no rule draws a die from the seeded generator: the reducer stops at the roll, the table asks the seat whose roll it is, and the throw enters the log as a `dice/rolled` event, so a replay produces the same game.

## How a roll is asked for

Every place a rule rolls says what for, in the words the table uses (`DiceAsk` in `src/lib/game/random.ts`): `d6(rng, 'main', { what: 'to see if you are lost', hint: "4+ means you're okay" })`. With physical dice on and nothing scripted on that stream, `d6` and `dice` throw `DiceNeeded` before anything is changed (the reducers are pure). `reduceOne` catches it and holds the event in `state.awaiting`: the seat (the ask's `seat`, else the event's, else the current seat), the stream, how many dice, the prompt `Roll a D6 {what}; {hint}` and the throws already made for the same event. Every other event is refused while a roll is awaited.

`dice/rolled { seat, values }` appends the values to the stream's script and applies the held event again from the same state; its earlier throws are read back in order, and it either completes or stops at the next roll. A throw of several dice (the roll for first player, a mountain's height, the natives' reaction) is asked for as one. The dice an event used are dropped from the state once it completes.

The table shows the ask at the rolling seat's edge (`DicePrompt.svelte`): the prompt, the throws already made for the action, what the dicecam sees, and six faces to tap when there is no camera, or when it misreads. A scrim holds the rest of the table still. When the last die of an action is in and the event it held is applied in full, what the dice decided stays at the edge for two seconds (`DiceResult.svelte`, prompts 54 to 56): the lines the throw made, every number explained, with Carry on to go sooner. The roll for first player apart, every ask lingers so: a step's lines after its last die, a card's, the hunt's, a fight's, the loot's. When the same event goes straight on to another ask nothing lingers, that ask showing the lines so far instead.

A die asked for part way comes with the lines so far (prompts 34 and 56): a rule with the game state at hand notes how the game stood when the dice ran out (`noting(run, { state })` in `game/random.ts`; `reduceOne` takes the lines that state holds beyond the one the event was applied to), a rule deeper down notes the line it is still writing (`noting(run, { making })`: the fight so far, the card's dice so far, the meal before the sickness dice), and the exploration step attaches its lines itself (`DiceNeeded.sofar`). The prompt shows them as the log will, the verdict on the same line as the die, and lists a throw on its own only until its line is written. So the nerve's ask shows the reaction's line, the surprise's the fight so far, and an oasis or an escape asked as a turn opens shows the previous seat's hunt.

## The dicecam

The dicecam is the table's own camera, shown on a canvas in the south-west corner of the board, read by the dice analysis of the WebCamTool project (https://github.com/egirard/WebCamTool, the camera pipeline behind its Yahtzee page). The table does not bundle that analysis: WebCamTool packages it as module workers, hosted with its site (`https://egirard.github.io/WebCamTool/dicecam/engine.js`, its `docs/dicecam-engine.md`), and the table loads the engine at runtime.

**The division.** The table (`Dicecam.svelte`) owns the camera, so the permission is the table's own: it asks for the camera the moment physical dice are switched on, draws every frame on its canvas letterboxed, and draws the engine's last reading over the picture the way the Yahtzee page draws its overlay (`overlay.ts`: the tray's floor dashed in orange, each die's outline in blue, its box in red, its top face in green, the pips in magenta, a confidence bar along its foot and the value above it, in orange when the die lies askew). The engine owns the analysis: motion (calibrating, rolling, settled), the tray, the dice, and the roll bookkeeping (one roll id per throw, removals, askew). The table posts one frame at a time as an `ImageBitmap` and the next only after the engine's `tick` for the last, so frames never queue up behind an analysis and the rate adapts to the machine. The dicecam is kept mounted for the whole game so the engine stays calibrated; the page moves it with CSS only, parked in the corner and brought to the middle of the board, turned toward the roller, while a roll is asked.

**Loading the engine** (`engine.ts`). A worker script must be same-origin with the page that creates it, so the table starts the engine through a blob module that imports the hosted file; GitHub Pages serves it with `Access-Control-Allow-Origin: *`, which that import needs. The engine's chunks, the detector worker it starts (the analysis proper, in a worker of its own so the motion loop never waits on it) and the digit model resolve beside the engine, from its real URL. The URL comes from `VITE_DICECAM_URL` (the deploy job sets the hosted engine; a value starting with `/` is taken under the app's base path). Without it the prompt says there is no dicecam and the faces do the work. The engine must say `ready` within thirty seconds, else the dicecam reports it could not be loaded.

**Status** (`DicecamStatus`): `starting` (the camera is being asked for), `loading` (the camera streams, the engine is not up yet), `active`, then the camera's failures (`permission-denied`, `no-camera`, `camera-in-use`, `unsupported`, `reconnecting` after the stream ended, `error` once three reconnections failed) and `no-engine`. The prompt's status line words each; the dicecam's own corner shows a short note while it is not active, and the engine's motion state beside its label while it is.

### Protocol (version 2)

The types are `EngineMessage` in `src/lib/features/dice/dicecam.ts`, a reading of WebCamTool's `src/lib/dicecam/protocol.ts`. To the engine: `{ type: 'frame', bitmap, timestamp }` (transferred) and `{ type: 'reset' }` (after the camera restarted). From the engine:

| Message | When |
|---|---|
| `{ type: 'ready', protocol: 2, version }` | the engine and its detector are up |
| `{ type: 'tick', motion: { status, progress? }, frame }` | every frame: the motion state, and the next frame may go |
| `{ type: 'roi', roi }` | the tray's floor as last found (`{ detected, polygon, confidence }`), or `null` |
| `{ type: 'rolling', … }` | motion: a throw is under way; the overlay is cleared |
| `{ type: 'removed', remaining, … }` | dice taken out of the tray |
| `{ type: 'settled', rollId, kind, frame, dice: [{ value, confidence, askew, boundingBox, contour, face, pips, … }] }` | a reading of the settled tray, the dice left to right, with the geometry the overlay draws; `rollId` names the throw |
| `{ type: 'error', message }` | something failed; the engine goes on where it can |

### Reading a throw

`consider` in `dicecam.ts` judges each settled reading against the ask, die by die (prompts 20, 21 and 36). What already lies in the tray is never read as the throw: when an ask opens, the table takes the tray as it lies (the engine's last reading) and the throw last taken, whoever threw it, as lies to ignore, each die by its face and where it lay. In a reading, a die with the same face up within a die's width (`MOVED_LESS_THAN`, 0.06 of the frame) of where a die of those lies lay is that die, resting; every other die is the throw: a die tossed in beside the others, one picked up and rolled again (a new face where it lay, or the same face a die's width away), or the whole tray thrown afresh. A reading in which every die rests is the tray as it already lay, whatever the engine calls it, and the status line waits for a roll ("Waiting for a D6 roll"); the dice thrown are the throw, whatever the engine calls them. The engine's `rollId` is not the judge of a throw: it follows the engine's motion detector, which a hand reaching in trips (the same lie gets a new name) and a single die tossed in from outside the picture can miss (a new lie keeps the old name); it decides only for a die whose place is unknown. At the start of the run, before any reading is known, the engine's first reading is the tray as found, unless the engine saw the dice roll first.

A die read with **another face where a die lay** is a throw only once the engine has seen the dice move (`rolling`) since the last throw was taken (prompt 58, `Watch.motion`). Until then it is a resting die whose face flickers in the engine's reading, and it rests like the others (counted as `misread` in the console's line: "lying there already, 1 misread"). This is the cause of every die the capture showed taken twice (scenario 041, docs/diagnostics.md): a die left lying from a throw was read 3, then 1, then 3 again, two agreeing readings each time, and each change was taken as a throw for the next ask. The table remembers whether the engine has seen motion since the last throw was taken and opens each watch with it, so a throw made before the ask opened still counts. The trade: a die picked up and rolled again without the engine seeing it move, landing on its own spot with a new face, is left alone until the next throw is seen; a die landing anywhere else is read as before.

A throw the tray holds whole (`DICE_AT_HAND`, four dice or fewer) is taken when the dice thrown are the count asked for: three dice lying from the last throw and a fourth tossed in beside them is a throw of one die, as is one of the three picked up and rolled; the three resting are left out. It is also taken when the tray shows exactly the count asked for and anything in it moved (the four thrown again, one of them happening to land where it lay with the same face up), since the tray as a whole is then a new throw. A throw of fewer or more dice than asked for is not taken, and the status line says what was thrown and what is wanted ("2 dice thrown, one die wanted"). Every die of the throw must be read with confidence 0.7 or better and none askew (a resting die may be read as it is), and two consecutive readings of the same throw must agree before the values are sent as `dice/rolled`. A die picked up and rolled that lands where it lay with the same face up cannot be told from a die left alone (nor, with the toss unseen by the engine, one landing there with a new face, prompt 58), and a rolled die that knocks another a die's width along is read as two dice thrown. The table logs each reading it judges to the browser console (`dicecam <rollId> <face>@<x>,<y> … <verdict>`, the verdict saying how many dice rest: "taken 5, 3 lying").

A throw of more dice than the tray holds (the loot of a village, a die a warrior; the shots at a card's animals, a die an askari) is gathered over several throws (prompt 33). The reducer takes a `dice/rolled` of any number of dice up to what is still wanted and keeps them in `awaiting.have` until the count is in, then applies the held event; `dice/rolled {auto: true}` has the table roll the rest from the stream's generator, the same on every client. The dice rolled go into the stream's script where the held event reads the throw (`DiceNeeded.at`), after whatever it reads before and ahead of anything a scenario scripted for later, so a scripted game can turn physical dice on part way. On such an ask `consider` takes the dice thrown, one or more, up to what is still wanted (never more), each reading taken a lie for the next, so the player may roll the dice one at a time, letting them pile up in the tray, or pick some up and roll them again while the others rest, or throw them all together (prompt 36); the prompt shows the dice in so far ("4 of 12 in"), each tapped face goes in at once, and "Roll the rest" sends the `auto` event. The status line says what is still wanted ("Waiting for a throw; 8 more dice wanted").

## Setting a die right

A die the dicecam misread can be set right after the fact (PROMPTS.md, prompt 37). Every die in the log knows the throw it came from: `dice/rolled` puts each die into the stream's script with its source (`DieSource`: the event and the die's place in it, kept beside the script in `RngObject.sources`), the generator notes each scripted die as a rule reads it (`RngObject.read`, in reading order, with physical dice on), and once the event has run its new log lines are matched to the dice read, in order by value (`src/lib/game/sources.ts`), a die rolled and not logged being skipped; the lines so far on a prompt are tagged the same way. A tap on such a die, at the rail's latest line, in the open log or among the prompt's lines so far (`DiceRoll` with `ontap`: the dice are one touch target, the die nearest the finger is meant), opens a radial menu of the six faces round the die (`RadialMenu.svelte`, as WebCamTool's Yahtzee page offers on a die in its feed: six wedges, 1 at the top and on clockwise, the face the die shows marked, an X in the centre to leave it), turned to the seat. The face chosen is sent as `dice/corrected { seat, eventId, index, value }`; the throw as rolled is never rewritten.

`reduce` applies a correction by folding the game again from its events with that die's value changed in its throw, and lets it stand only if the game would have gone on as it did: every later event accepted or refused as before, and every later throw answering the ask it answered (the lost check set from a one to a four would turn the hunt's die rolled after it into the terrain's direction, so it is refused). A correction that stands marks the die as set by hand (`Roll.from.corrected`, a dot on the die in the log) and the game goes on from the corrected state, which may be a new ask (the lost check found the way after all: the terrain die is asked). A correction refused is a diagnostic with the reason ("the die stays a 1: the throw for the hunt that followed would answer another ask (for the direction of the terrain to copy)"), which the table shows at the seat's edge over the held table until the player carries on; the game is as it was. A die the table rolled itself (`auto`) was never read from the tray and cannot be corrected. A correction is never undone, and a reload replays corrections with the throws.

A die can also be checked in the picture. Each throw the dicecam reads goes to the game with where its dice lay (`dice/rolled { lay }`, a fraction of the frame per die), so a tap on the dock's canvas (`Dicecam.svelte` `ontap`, the tap turned back through the dock's rotation) finds the die of the game lying there: the latest throw with a die within a die's width of the tap, its face as the game has it now, corrections that stood applied (`dieAt`). The engine has no request to read one die again (its protocol reads the settled tray over and over, and nothing else), so the table takes the readings that follow the tap: the die within a die's width of where it lies is read once more in each, and two consecutive readings that agree are its face (`rechecked`). Another face than the game has is sent as `dice/corrected` as the menu would send it ("Read again: a 6, not a 2" over the picture); the same face leaves the game be ("Read again: still a 2. Tap it again to set its face"); a die gone from the tray ends the check. A second tap on the same die, during or after the check, opens the radial menu over the picture instead, turned with the dock. A tap beside the dice, or on a die that is not a throw of the game (dice from before the game, dice moved about between throws), says so over the picture and does nothing. The dock's note and any check are dropped when the dice roll or a throw is taken.

## In E2E builds

Every scenario's Chromium has a camera: its fake device playing `tests/e2e/fixtures/dicecam-tray.y4m`, one still frame of a synthetic tray (640×360, four blank dice in a row; `--use-file-for-fake-video-capture` in `playwright.config.ts`, with the camera permission granted). Only a table with physical dice on asks for it. `build:e2e` sets `VITE_DICECAM_URL=/dicecam-stub.worker.js`, a stand-in engine that takes the frames and makes nothing of them, answering each with a settled tick, and repeats to the table whatever the scenario posts on the `dicecam-stub` broadcast channel. Scenarios 037, 018 and 041 speak for the engine that way, in its protocol, with readings whose geometry is the tray's (the i-th die of a reading at the tray's i-th place, a fifth and beyond in a second row), so the overlay is drawn where the dice are and a tap on the canvas at a place of the tray finds the die there; they enter other throws by tapping faces. The real analysis is never exercised by a test.
